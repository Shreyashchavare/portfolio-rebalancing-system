## 1. Executive Verdict

### Recommendation: **READY WITH DOCUMENTED LIMITATIONS**

The YottaFlex Portfolio Rebalancing System has been thoroughly inspected, executed, and tested against live services. It demonstrates exceptional engineering integrity, mathematical determinism, and robust security boundaries:

* **Real Persisted Database Records:** All portfolio valuations, drift computations, proposed lot-sized trades, simulated post-trade cash balances, and policy constraint evaluations are calculated live against PostgreSQL 17 (`portfolio_rebalancing` database).
* **Genuine AI / Policy RAG:** Semantic policy search uses genuine FastEmbed ONNX vector embeddings (384-dimensional cosine similarity), and grounded natural language explanations are genuinely generated by a live Ollama container running `llama3.2:latest`.
* **Zero Fabrication Principle Enforced:** There are no hardcoded portfolio valuations (`$1,050,000`), sample AAPL trades, or fabricated time-series fallbacks. Unsupported historical NAV curves were purged in favor of strict point-in-time financial truthfulness.
* **Deterministic Financial Core:** Valuations, tiered transaction fee deductions ($127.3011), cash solvency checks, and lot-size rounding are executed exclusively by pure Python algorithms. The LLM is sandboxed from financial mathematics.
* **Fail-Closed Dual-Key Security:** Production mode (`APP_ENV=production`) strictly blocks mock authentication. Role-Based Access Control (RBAC) separates Customer (`VIEWER`), Analyst (`PORTFOLIO_MANAGER`), and Compliance Reviewer (`REVIEWER`). Hard constraint violations permanently block proposal approval (`HTTP 422`).
* **Documented Limitations for Evaluators:**
  1. *Host Port Mapping:* On the local Windows evaluation machine, host port `5432` is occupied by a pre-existing host service (`postgresql-x64-18`). The official Docker PostgreSQL 17 container is bound to host port `5433:5432` and configured in `.env`.
  2. *Active Dataset Selection:* The live PostgreSQL database is populated with the verified starter dataset (10 portfolios, 20 instruments, 600 market prices, 40 target allocations, 28 constraints). The full-scale dataset (1,000 portfolios, 5,000 instruments, 1,250,000 market prices, 197 MB SQL seed) is generated and validated in `data/full/`, but not loaded by default to prevent container memory exhaustion during quick evaluations.

## 7. Role-Based Access Control (RBAC) & Security Findings

1. **Authentication Architecture:**
   * Authoritative reviewer identity is extracted exclusively via `get_current_reviewer` from Bearer tokens in `Authorization` headers. Client-supplied user headers are ignored.
   * `APP_ENV=production` boundary: `get_auth_verifier()` raises a `RuntimeError` if mock authentication is enabled in production.
2. **Separation of Duties:**
   * Customer (`VIEWER`): Read-only view. Mutation endpoints (`/rebalance/proposals`, `/approve`, `/reject`) return `HTTP 403`.
   * Analyst (`PORTFOLIO_MANAGER`): Generates proposals, runs drift analysis, simulates trades. Cannot approve proposals.
   * Reviewer (`REVIEWER`): Dedicated dual-key approval desk. Must supply justified non-empty rejection notes.
   * Administrator (`ADMIN`): Access to reference data architecture, data quality staleness rules, and engine diagnostics.
3. **Frontend Route Guards:**
   * Protected routes enforce role membership. Unauthorized URL visits redirect to `/unauthorized` or role-default views.
4. **Secret Protection:**
   * Zero bearer tokens or credentials leaked to browser logs (audited via Chrome DevTools Protocol).

### 14.5 Data Model Documentation & 15-vs-16 Table Discrepancy Resolution

#### 1. Resolution of the 15-versus-16 Table Discrepancy
An earlier audit noted a discrepancy between 15 business entity tables and 16 tables in PostgreSQL (or 17 in SQLite). The exact architectural explanation is:

$$\text{PostgreSQL Total Tables (16)} = 15\text{ Core Business Domain Tables} + 1\text{ Technical Infrastructure Table}$$

1. **15 Core Business Domain Tables:**
   `investor_profile`, `portfolio`, `instrument`, `holding`, `market_price`, `target_allocation`, `fee_schedule`, `constraint`, `constraint_instrument`, `rebalance_proposal`, `trade`, `policy_documents`, `policy_chunks`, `workflow_runs`, `audit_events`.
2. **1 Technical Infrastructure Table:**
   `migration_history` (manages schema migration execution history and checksums in PostgreSQL).
3. *(SQLite Note: In SQLite test runners, the engine automatically creates a 17th internal metadata table `sqlite_sequence` to track autoincrement integer primary keys).*

#### 2. Core Entities Specification Dictionary

```
+---------------------------------------------------------------------------------------------------------------------------+
| ENTITY                  | PRIMARY KEY        | FOREIGN KEYS                    | LIFECYCLE / VALIDATION INVARIANTS        |
+---------------------------------------------------------------------------------------------------------------------------+
| investor_profile        | investor_id (STR)  | None                            | Risk categories: CONSERVATIVE / MOD / AGG |
| portfolio               | portfolio_id (STR) | investor_id -> investor_profile | Base currency USD; rebalance threshold %  |
| instrument              | instrument_id(STR) | None                            | Active flag; lot_size multiple >= 1.0     |
| holding                 | holding_id (STR)   | portfolio_id, instrument_id     | Quantity >= 0.0000; point-in-time date    |
| market_price            | id (INT AUTO)      | instrument_id -> instrument     | Price > 0; unique(instrument_id, date)   |
| target_allocation       | id (INT AUTO)      | portfolio_id -> portfolio       | 0 <= weight <= 100; Portfolio sum = 100%  |
| fee_schedule            | fee_sched_id (STR) | None                            | Tiered bps + fixed; min/max fee clamps    |
| constraint              | constraint_id(STR) | None                            | HARD (blocking) vs SOFT (warning)         |
| constraint_instrument   | composite (PK2)    | constraint_id, instrument_id    | Many-to-many bridge for exclusion lists   |
```
